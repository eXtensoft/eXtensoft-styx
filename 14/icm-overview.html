01 — WHAT IT'S FOR

Intent

ICM targets one specific job: sequential, human-reviewed AI workflows — content pipelines, report generation, slide decks — where a person checks the output at each step before moving on.

It replaces framework-level orchestration with filesystem structure. Numbered folders represent stages. Plain markdown files carry the prompts and context that tell a single AI agent what role to play at each step, while local scripts handle mechanical work that doesn't need AI at all.

The pitch is deliberately narrow: not "better than LangChain, CrewAI, or AutoGen" in general, but "for this specific class of workflow, you don't need them at all."

02 — HOW IT WORKS

Methodology

Five design principles, each lifted from an established practice:

  1. One stage, one job.

    Each folder performs a single transformation — fetch, filter, format — never more than one. Mirrors Unix's "do one thing" rule and Parnas's information-hiding criterion.

  2. Plain text as the interface.

    Stages hand off through markdown and JSON — nothing binary, nothing proprietary. Any text editor can inspect or modify any artifact.

  3. Layered context loading.

    Agents load only what the current stage needs. Reference material (stable rules, style guides) and working artifacts (this run's actual content) are kept structurally separate, so the model isn't left to sort constraints from input on its own.

  4. Every output is an edit surface.

    Each stage's output is a file a human can open, edit, and save before the next stage reads it. The next stage picks up whatever was left there.

  5. Configure the factory, not the product.

    A workspace is set up once — voice, brand, structural conventions — then every run reuses that configuration to produce a new deliverable.

03 — WHAT IT TAKES FOR GRANTED

Assumptions

  • The workflow is genuinely sequential — stage 2 can't start without stage 1's finished output.
  • A human wants to review and edit between steps — this is treated as a feature, not overhead.
  • The same pipeline runs repeatedly with different input — built for a factory, not a one-off task.
  • One capable orchestrating agent, given the right scoped context per stage, can competently execute each step — no need for multiple agents negotiating independently.
04 — WHERE IT HOLDS UP

Strengths

+ Zero framework dependency

  • A workspace is just a folder — copy it, zip it, git commit it, hand it to someone with no dev environment.
  • No server to configure, no deployment step, no environment to replicate.

+ Cheap, effective context

  • Each stage sees roughly 2,000–8,000 focused tokens instead of a 30–50k monolithic prompt.
  • Avoids the "lost in the middle" degradation from burying relevant instructions in irrelevant material.

+ Observability for free

  • No logging layer or dashboard to build — state is just files you open and read.
  • Aligns naturally with emerging regulatory expectations around staged review and audit trails.

+ Low barrier to change

  • Non-technical users have edited stage behavior directly in markdown — tone, constraints — with no developer involved.
  • A workspace can be duplicated and retargeted to a new format without rebuilding from scratch.
05 — WHERE IT STRAINS

Weaknesses

− Not built for concurrency

  • Real-time, tightly-coordinating multi-agent loops need message-passing infrastructure this approach doesn't provide.
  • Local-first by design — many simultaneous users would require the infrastructure it was built to avoid.

− Awkward automated branching

  • A human can choose between stages based on what they see — but branching driven by the AI's own mid-pipeline decisions pushes the system back toward being a framework.

− No real debugging yet

  • If a later stage's output is subtly wrong, there's no automated way to trace it to the file or instruction that caused it — today that's done by manually re-reading contracts.
  • Provenance IDs, cross-stage verification, and markdown "breakpoints" are proposed, not built.

− Thin, self-reported evidence

  • Practitioner observations come from an invite-only, self-selected community of 52 via informal conversation — not structured interviews or instrumented logging.
  • No controlled comparison exists against monolithic prompting on the same tasks.
  • All testing used a single model family — cross-model generalization is unverified.
06 — DOES IT ACTUALLY WORK

Efficacy

No rigorous benchmarking exists yet. What's reported comes entirely from practitioner conversation, not instrumented measurement:

  • Edit pattern

    A "U-shaped" curve — heavy human edits at the first stage (setting direction), light edits mid-pipeline, heavy edits again at the final stage (aligning output with earlier decisions). Reported by 30 of 33 practitioners surveyed informally.

  • Accessibility

    A handful of users with no coding background built and ran working pipelines unaided, using the workspace-builder's guided setup.

  • Outside adoption

    Reported use at a university lab and two other organizations — but actual outcomes are under NDA and unreported.

  • Net read

    Plausible and consistent with known context-window research, but the efficacy claims remain anecdotal rather than measured.

08 — SUMMARY

Bottom line

VERDICT

ICM isn't new AI capability — it's an organizational discipline for one specific class of problem: sequential, human-reviewed, repeatable content or document pipelines run through a single coding agent. For that niche, it's a genuinely reasonable alternative to standing up a multi-agent framework. It is not a substitute where you need concurrency, dynamic agent negotiation, or automated branching — and its efficacy claims currently rest on a small, self-selected practitioner community rather than controlled evaluation.
