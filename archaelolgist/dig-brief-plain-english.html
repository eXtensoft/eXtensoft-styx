The dig · what you hand it

The Dig Brief

What you hand the Archaeologist so it can run one dig: a complete, self-contained briefing — everything it needs to read a codebase and come back with a specification, packed into a single folder.

The name is the point. You don't send an archaeologist to a site with a vague email. You hand them a brief — here's the site, here's the method, here's what to bring back.

The one hard rule

Completely self-contained.

This is the rule everything else hangs on. A Dig Brief has no external dependencies and no external references. Everything it needs is inside the folder — the instructions, the standard it writes to, the tool that runs the dig, the checker that validates the result.

Any programmer knows the pain this avoids: nothing to install, no "works on my machine," no broken link to a file that moved. Drop the folder onto any machine and it just runs. (We learned this the hard way — an early version of the instructions pointed at a document that wasn't included, and a fresh run couldn't reach it. Self-containment closes that door for good.)

What's inside a Dig Brief

DIG-PROMPTthe instructions — how to dig, and the honest-not-confident posture
schema/the standard — the shape the output has to fit (a typed spec for a system's intent)
runner/a thin bit of code that hands the brief to the Archaeologist and collects what comes back
validate.pythe checker — confirms the output conforms, zero errors

That's it: a briefing, the method, and just enough machinery to run it.

Two version numbers, on purpose

The toolkit and the standard version separately.

A design choice a programmer will appreciate. Two things get versioned, and they're kept apart:

  • The standard (the shape of the output) has its own version — right now, 0.4.1.
  • The Dig Brief (the toolkit — the prompt, the runner) has its own version.

Why separate? They improve on different clocks. Just recently we fixed a bug in the prompt and the validator — but the standard didn't change at all. If the two shared one version number, you couldn't tell those two toolkits apart. So a Brief carries its own version, and pins exactly which version of the standard it ships with.

Versions sit side by side

Run two of them and diff the results.

The versions live in parallel folders, all present at once — deliberately. You can take the same codebase, run version 1.0 and version 1.1 against it, and diff the two results: did the newer toolkit recover more? Miss something? With ordinary version tags you'd only have one checked out at a time; here you run them head to head.

Every run is stamped

Reproducible, and comparable.

When a dig finishes it doesn't just drop loose files. It writes an output package — the recovered spec, the notes, and a small manifest recording when it ran, which Brief version, which standard version, and exactly which commit of the target repo it read.

Any dig is reproducible — you know precisely what produced it — and comparable. Nothing's a mystery six months later.

Built here, run there

Experiment and dependence, kept apart.

Briefs are built and refined in one repo (where the standard grows) and run in another (the everyday workspace). You tinker with the toolkit over here; you run real digs over there, against a stable, frozen version. The place you experiment and the place you depend on are kept apart on purpose.

The whole point

A dig you just run.

Before all this, a dig was a clever prompt a person had to assemble by hand every time — gather the instructions, the standard, the right model, wire it up. A Dig Brief turns that into a thing you just run: hand the Archaeologist a versioned briefing, get back a stamped, validated specification. Repeatable, reproducible, and honest about its own version.

The flavor, not the fine print. The full spec — every folder and rule — is in docs/DIG-BRIEF.md.
