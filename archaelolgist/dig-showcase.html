The idea

Code isn't intent. It's the most degraded copy of it.

Intent → requirements → design → code: a game of telephone where every hop drops signal, and the docs start rotting the moment they're written. A dig runs that backwards. It reads the code (plus whatever docs survived) and recovers the intent as typed data — cold, exact, and rebuildable.

The bar isn't "a nice summary." The bar is a reconstruction test: could someone rebuild this system — in any language — from the spec alone, and preserve what it was for? That's what the output has to pass.

A real dig

Meet BladeRunner — a doc-less desktop app from 2011.

Our test subject is a WPF desktop application called BladeRunner (the codebase is full of Voight-Kampff jokes — questions are "elicitations," provisional types live in a "suspect" namespace). ~176 files, ~11k LOC, zero third-party dependencies, and the hard part: no documentation whatsoever. Nothing to read but the code.

Here's what came back.

recovered · purpose

appspec.purpose.primary

Let an author design a self-contained Data Acquisition Workflow — an ordered, nestable set of questions (elicitations) with typed responses, declarative branching/skip logic, validation, reusable rating scales and per-question screen layout — and then run that workflow to elicit and capture answers as typed, model-bound datapoints, without hand-coding a screen or a rule.

In plain English: it's a tool for building and running dynamic questionnaires — branch logic and screen layouts resolved at runtime as data, so you add a new layout without touching code. Almost certainly health-insurance. None of that is written down anywhere — it was reconstructed from the class model.

Why a skeptic should care

The interesting part: it refuses to bullshit you.

Any language model will happily invent a confident story about your code. This one is built not to. That restraint is the whole product. Three ways it stays honest:

1. It names dead things as dead. BladeRunner looks finished — full save/load, a five-state auth session, a serializable object model. It isn't. The dig caught it:

flagged · half-wired prototype

appspec.liveness — classification: debt-obscuring

Startup persistence (Bootstrapper.InitializeWorkspace) is entirely commented out. Presentation strategies load from a hardcoded c:\local\presentationstrategys.xml. Authentication is faked — a one-second timer auto-authorizes everyone. The load path seeds dummy "Question-0" placeholders.

It didn't paper a half-finished prototype over as a working product. Its verdict: this telos is aspirational, not achieved.

2. It catches false evidence. The only "owner" anywhere in the code was an unedited Visual Studio template default. It flagged that as a lie instead of reporting "built by Microsoft":

flagged · false signal

appspec.findings — kind: drift

The only ownership metadata — AssemblyCompany "Microsoft", Copyright "Microsoft 2011" — is an unedited Visual Studio template default, not a real ownership claim.

3. It marks "unknown" and means it. With no docs to state the why, the dig left the verdicts open rather than guessing — and listed exactly what it couldn't know:

  • Who owns or commissioned it (the "Microsoft" copyright is a placeholder)
  • Whether the domain is insurance underwriting, care assessment, or general questionnaires
  • Whether the runtime window is the product, or the authoring surface is
  • Whether it ever shipped — or was abandoned as a prototype

A wall of "high confidence" on a rotten estate would be a lie. The mix — high on the what, unknown on the why — is the honest coverage.

— from the dig's own notes

And it records deliberate absence as a first-class fact, not a gap. There's no database, so it said so, with the evidence:

recovered · deliberate exclusion

appspec.exclusions — exc-no-database

"No database or data-access layer; persistence is local XmlSerializer documents only." reason: "Workflows are portable documents; a desktop authoring tool needs no server-side store." evidence: implementation · BladeRunner.csproj (no data assemblies)

"We checked, and there is none" is a different statement from "we didn't look." The spec can tell them apart.

How it works

Three pieces, in plain English.

01The Dig Prompt

The briefing that makes a fresh AI dig this way — best readings carrying their confidence, two evidence channels (what the code does vs. what the docs claim) held against each other, dead code named not laundered. The method, written down.

02The Dig Brief

A self-contained, versioned package you hand the digger ("the Archaeologist"). Everything it needs is inside — prompt, the spec standard, the validator. Run two versions against the same repo and diff the results.

03The AppSpec

The code-free standard the output conforms to: a typed shape for a system's intent. So the result is data you can validate, query, and rebuild from — 21 populated sections here, machine-checked to zero errors — not prose that goes stale.
